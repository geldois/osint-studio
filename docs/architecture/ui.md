# UI — what it does

The frontend's non-Whiteboard chrome (login, settings, ingest, account menu, theme toggle) is built from
shadcn/ui components vendored into `src/components/ui/`, generated by the shadcn CLI — `components.json` pins
the exact configuration — rather than hand-written Tailwind utility classes repeated per screen.

## Decisions

Base UI was chosen over Radix as the accessibility primitive underneath every interactive component: the project
had no existing Radix dependency creating inertia toward it, and Base UI is the primitive the shadcn CLI itself
promoted to default starting with its March 2026 rewrite. The "Nova" preset (Lucide icons) was picked because it
already matched what this project used before adopting shadcn, not because it's the CLI's own default.

The whole app renders in one locally vendored monospaced face (ZedMono Nerd Font Mono, `src/app/fonts/`) instead
of Geist Sans paired with a separate Geist Mono for code-like text — a deliberate compact, terminal-flavored look
rather than the CLI preset's own choice, applied to both the `--font-sans` and `--font-mono` tokens so nothing on
screen falls back to a proportional face. The one cost accepted for it: a Nerd Fonts build embeds every icon
glyph the patcher adds on top of the base face, so the vendored file is several megabytes heavier than an
unpatched monospaced font would be — paid once at load (`next/font/local`, swap display) rather than per
request.

Every color token in `globals.css` is pulled from Radix Colors' published scales rather than picked by eye or
left at the shadcn CLI's own generated gray — a neutral scale for background/surface/border/text, plus one
accent scale for anything interactive that needs to stand out (selected states, focus rings, links) and one
scale each for destructive and warning feedback. Radix Colors was chosen over a competing token set considered
at the same time (Catppuccin, popular in terminal-flavored tools and a close aesthetic fit) because it ships
contrast guarantees between each scale's own steps rather than a palette that merely looks coherent, and because
Base UI — this project's accessibility primitive — is the spiritual successor to the same team's Radix
Primitives, so the two already share a design lineage. Light and dark pull the matching light/dark variant of
each scale; nothing is computed or interpolated, every value is the literal hex the scale publishes.

Corner rounding was pulled in from the softer, more rounded default that read as generic — the single `--radius`
token driving every derived radius, so every already-styled surface picked up the change without individual
edits. Pulling it in too far turned out to have its own failure mode: a small control (an icon button, a
segmented toggle's active item) with the same proportionally-scaled-down radius as a large one reads as
noticeably squarer sitting next to a bigger surface using the same base token, since a few pixels of curve
disappear against a small filled area in a way they don't against a thin border on a bigger shape. `--radius`
settled at a value small enough to still read as deliberately squared-off rather than the generic default, but
large enough that small filled controls don't look like they lost their rounding entirely — a couple of the
smallest controls (the ingestion trigger, the view switch's active state) were also bumped to match their
container's own radius token exactly rather than a smaller derived one, instead of relying on proportional
scaling to keep them looking related. Body text now defaults to the bold weight of the vendored monospaced
face, rather than its regular weight, for a heavier, more deliberate feel — the font file already carried both
weights for headings, so this only changed which one text inherits by default.

The Whiteboard's own visual surface (`src/components/detail-panel/`, `src/components/data-table/`, the Whiteboard
header) now runs on the same component set — `Card`/`Button`/`Input`/`Table`/`ScrollArea` — once the chrome-screen
pass above proved the pattern held. `src/components/nodes/` and `src/components/edges/` keep their own custom
React Flow renderers, since no shadcn primitive maps to a graph node or edge.

A relationship edge's list of relationships always lists every incoming one before any outgoing one, a fixed order
rather than whatever order the backend happened to return them in, and renders inside a real `Popover`, opened by
clicking the diamond marker — a deliberate UX choice: relationships stay hidden until asked for, trading
always-visible detail for a quieter Whiteboard on graphs with many edges. Its one known gap: the popup doesn't
track the diamond during an
active pan or zoom while it's already open, since Base UI's positioning follows scroll/resize/layout-shift but not
a pure CSS-transform move — closing and reopening it re-anchors correctly. Fixing that live-tracking case would
need shared state between the Whiteboard and every edge just to close the popover on pan-start, judged not worth
it for that narrow a window.

Every other popover/menu in the app (the graph info button, the embedded ingestion flyout, the pattern picker,
the theme menu, the account menu) renders through one shared `Flyout` component instead of calling
`Popover`/`DropdownMenu` directly: at or above the `md` breakpoint it's a `Popover` anchored to its trigger,
below it a centered `Dialog` with its own header (title, optional back, close) instead of a small anchored
popup that would clip or crowd a narrow viewport. `DetailPanel` doesn't route through `Flyout` — it already
fills the viewport's height on mobile as a bottom-anchored panel, so a centered dialog would fight its own
layout instead of matching it.

Theme is `next-themes` (`attribute="class"`, `defaultTheme="system"`, `enableSystem={true}`) rather than the
project's own 40-line store it replaced. The defect that forced the swap onto `next-themes` in the first place
was the flash of dark theme on every load for a user who'd picked light: fixing it without the library means
writing the same blocking pre-paint script `next-themes` already ships, so keeping the hand-rolled store would
mean maintaining both. `enableSystem` and `defaultTheme` started as `false`/`dark`; both flipped once the
product requirement changed to following the OS preference by default, with light/dark as explicit overrides —
a later requirement, not a correction of the original choice. The theme toggle now exposes all three states
(system/light/dark) through a `Flyout` menu instead of a two-state icon toggle, and still reads `useTheme()`
behind a `useSyncExternalStore`-based mount guard — not a `useEffect` + `setState` mount flag — because the
project's React Compiler lint rule flags synchronous `setState` inside an effect body.

Form and Expansion errors that used to reserve a fixed line of text below a field or the Whiteboard header — present
or not — now attach to the field itself: a red or amber border plus a small icon whose native `title` carries
the message on hover, the same disclose-on-hover instinct the graph info button already used for its counts. The
layout no longer shifts or leaves blank reserved space when nothing is wrong, at the cost of the message not
being visible until the pointer (or, for touch, a tap-then-release) lands on the icon — judged acceptable since
the field it sits on is already the thing failing validation, so a user retrying it is already looking there.

Filtering the table, a node's relationship list, or the graph info button's list of expanded documents by type
is no longer exclusive-choice tabs, one type visible at a time. A filter button opens a checklist of every type
present, and every checked type becomes its own removable chip next to the button — so an analyst can see
people and companies together while addresses and phone numbers stay hidden, a combination tabs could never
express. No chip checked, or every type's chip checked, both mean the same thing as no filter at all, so
there's no separate "all" state to keep in sync with the individual ones. The table uses the same thin, themed
scrollbar as the rest of the app instead of the operating system's, forced by the floating-overlay change: the
OS scrollbar rendered partly underneath the detail panel once that panel became a floating overlay instead of a
column reserving its own width.

A person's detail panel and its row summary in the table now surface every field the backend's person schema
sends — birthdate, registration date, and registration status had been validated on the way in but never read
by anything that renders, so they existed in the parsed data without ever reaching the screen. Every other node
and edge type already exposed everything its own schema carries; this was the one gap, found by comparing the
backend's Pydantic schemas field-by-field against what the Whiteboard actually reads.

A node's relationship list dropped its own inner scrollbar entirely in favor of pagination (50 relationships
per page, with page numbers, previous/next, and a jump-to-last control) — a long list no longer means a scroll
region nested inside the detail panel's own scroll region, one scrollbar fighting another for the same mouse
wheel. Each relationship also stopped being a line of text with a bare arrow for direction and became its own
small card: a "para"/"de" badge (with an arrow icon and the primary accent color for outgoing, a neutral one
for incoming) above a miniature version of the counterpart's own graph Card — same colored left-to-right
border-by-type, same icon, same name-over-type-label layout the Whiteboard already uses for that node on the
graph. Reusing that visual language here, rather than inventing a second one for the same entity, is
deliberate: a person reading a relationship list should recognize a company's card as the same kind of object
they'd click on the graph, not a different, table-row-shaped thing that happens to represent it. The graph info
button's own list of previously expanded documents and their Revisions adopted the identical pattern — one
colored-border card per document, its Revisions as small clickable chips instead of a checkbox list — once it
became clear the same "which card family is this, and which of its versions is active" question showed up
there too, just phrased as "which Revision am I looking at" instead of "which relationship is this."

The table's columns are no longer a fixed five regardless of what's in view. Filtering down to exactly one node
type swaps the generic Tipo/Nome/Resumo/Relações columns for one column per attribute that type's own schema
carries — the same field list `nodeToRows` already produces for the detail panel, reused rather than
re-derived, so the two surfaces can never drift apart on which fields exist for a type. Selecting more than one
type, or none, falls back to the generic columns, since attribute columns from unrelated types side by side
(a person's age range next to a company's share capital) would be one wide sea of empty cells rather than a
richer view. Every row also now shows where its data came from — when it was fetched, and which provider it
came from — a gap the previous columns didn't cover; the table's own set of columns no longer needs a forced
minimum width per header, letting the browser's own default table layout size each column to its widest cell
instead. Both the generic and the per-type views paginate at 50 rows, applied after filtering rather than
before, so the free-text filter always matches against every row that meets the current type filter, not just
whichever 50 happen to be on screen.

## Consequences

shadcn's own `Card` component (`src/components/ui/card.tsx`) is a generic container, unrelated to this project's
own domain glossary's **Card** (a node's visual representation on the Whiteboard, `CONTEXT.md`) — the two names
coexist in different layers; see `CONTEXT.md`'s flagged ambiguities before assuming either sense.

Adding a component to any screen outside the Whiteboard means running the shadcn CLI (`pnpm dlx shadcn add
<component>`) against the pinned `components.json`, not hand-composing Tailwind classes — new primitives inherit
the token setup above automatically.
